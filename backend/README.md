# Бэкенд обработки научных PDF

Готовый сайт с подключённой моделью открывает корневой `start.cmd`. Он использует переносимый Python и каталог заданий `backend/runs/local`. Для запуска из клона см. [корневую инструкцию](../README.md). Ниже описан самостоятельный запуск API и контракт отдельного пакета модели.

Сервер принимает статьи в PDF или ZIP. По умолчанию используется шаблон для солнечных элементов. Свои критерии можно передать текстом либо отдельным PDF. Для каждого задания сервер запускает локальный пакет извлечения и выдаёт таблицы, ссылки на статьи и ZIP с результатами. Данные хранятся в `backend/runs` или в каталоге, переданном через `--jobs-dir`.

## Запуск на Windows

Для сервера достаточно Python 3.10 или новее со стандартной библиотекой. Команда запуска из корня проекта выглядит так.

```powershell
python .\backend\server.py --cors-origin http://localhost:5173
```

Локальная страница загрузки открывается по `http://127.0.0.1:8080/`. Она позволяет ввести критерии, следить за заданием, открыть страницы источников и скачать результаты. API работает по тому же адресу. Передайте в `--cors-origin` точный адрес отдельного фронтенда, если он работает на другом порту или домене. Этот параметр можно указать несколько раз. Для разработки доступна проверка `/api/health` до подключения пакета модели.

Собранный интерфейс NEXUS подключается через `--frontend-dir`. Для размещения за HTTPS-прокси укажите адрес сайта через `--site-origin`. [Запуск NEXUS](../frontend/README.md).

В архиве команды `model_bundle.zip` уже есть свой интерпретатор `runtime/python.exe`. После распаковки в `model_bundle` подключите пакет следующей командой.

```powershell
python .\backend\server.py --runner .\model_bundle\run_inference.py --cors-origin http://localhost:5173
```

По умолчанию `--runner` указывает на `model_bundle/run_inference.py` рядом с каталогом `backend`. Бэкенд ищет `runtime/python.exe` рядом со скриптом модели. Если у пакета нет своего интерпретатора, используется Python сервера. Путь можно задать явно через `--model-python`. `--port` задаёт порт, `--timeout` задаёт максимальное время одной обработки в секундах. По умолчанию оно составляет 1800 секунд.

## API для фронтенда

| Запрос | Результат |
|---|---|
| `GET /api/health` | Доступность API, наличие файла запуска и интерпретатора (`runner_configured`), размер очереди |
| `POST /api/jobs` | Отправляет задание и возвращает `202` с `job_id` и `status_url` |
| `GET /api/jobs/{id}` | Статус `queued`, `running`, `completed` или `failed`. При ошибке есть объект `error` с полями `code` и `message` |
| `GET /api/jobs/{id}/result` | Список файлов `files`, список PDF `sources`, замечания `warnings` и `download_url`. Для новых CSV `populated_columns` перечисляет колонки, заполненные хотя бы в одной строке |
| `GET /api/jobs/{id}/tables/{name}?offset=0&limit=50` | `columns`, `rows` и `total` для показа CSV. Значения ячеек возвращаются строками, максимальный `limit` — 200 |
| `GET /api/jobs/{id}/files/{name}` | Отдельный CSV, отчёт или `records.json` с привязками |
| `GET /api/jobs/{id}/sources/{name}` | PDF для открытия ссылки вида `url#page=5` |
| `GET /api/jobs/{id}/download` | ZIP с заполненными CSV, привязками и замечаниями при их наличии. Если заполненных CSV нет, архив недоступен |

При смешанной загрузке сервер передаёт пригодные статьи в обработку. В статусе задания поле `upload_issues` содержит имя и причину для каждого пропущенного файла, а для элементов ZIP также имя архива. Если всю загрузку пришлось отклонить до создания задания, эти подробности возвращаются в `error.file_issues`. В ответе `/result` поле `file_outcomes` описывает результат анализа каждого принятого PDF. Для старых заданий этот список может отсутствовать.

Перед публикацией новых заданий сервер сверяет одноимённые CSV с проверенной солнечной выгрузкой из `backend/reference/solar-test`. В сверку входят только PDF, у которых совпали имя и SHA-256. Если загружена одна статья, сравниваются строки только этой статьи. Пустые таблицы, несовместимые наборы колонок и статьи вне этого набора отмечаются в отчёте. Изменённые и односторонние строки учитываются отдельно. Например, запрос на одну метрику может оставить другие метрики только в проверенной выгрузке. Отчёт `reference-comparison.json` доступен из дашборда и входит в ZIP. CSV сохраняют значения, полученные в задании. Повтор с кешем проходит новую сверку перед выдачей.

Солнечный экспорт двух проходов использует `submission_format: solar-v1`. В ZIP входят семь CSV по шаблону, даже если часть из них содержит только заголовки. `publications.csv` включает строку с идентификатором каждого входного PDF. Свои критерии продолжают определять значения, которые нужно искать. Задания других предметных областей используют свою схему.

При отправке создайте `FormData` и добавьте каждую статью PDF или архив в отдельное поле `files`. Для схемы солнечных элементов оставьте `criteria` пустым или пропустите это поле. Свои критерии передайте текстом в `criteria` либо файлом в `criteria_pdf`. Для PDF можно выбрать физические страницы в поле `criteria_pages`, например `3-6`. Браузер сам формирует `Content-Type`. После `202` опрашивайте `status_url`. По завершении `result` возвращает URL файлов и таблиц. В `archive_files` перечислены файлы ZIP, а `download_url` равен `null`, если данных для архива нет. ZIP сохраняет полный комплект из семи солнечных CSV и таблицу `Efficiency.csv`, когда они созданы, в том числе файлы с одними заголовками. В `sources` есть `name` и `publication_id` для сопоставления с CSV. Для открытия статьи используйте физический номер страницы из `source_page`. Солнечный профиль сохраняет рамки ячеек в `records.json`, массив `records`, например в `sources.value.bbox`. Координаты заданы в пунктах PDF от верхнего края страницы.

Один сервер обрабатывает одно задание модели за раз и держит до восьми заданий в очереди. Два запроса могут загружать файлы одновременно. При заполненной очереди или ожидании слота загрузки дольше пяти секунд API отвечает `429`. Лимиты задания — 128 МиБ входящего запроса, до 100 PDF, до 64 МиБ на PDF и 256 МиБ после распаковки. Пути внутри ZIP используются только для поиска PDF. Имена PDF в одном задании должны различаться, в том числе без учёта регистра. При перезапуске готовые результаты остаются доступны. Оборванное или ожидавшее задание получает статус `failed` и его можно отправить заново. Используйте один экземпляр сервера на каталог заданий.

## Контракт пакета модели версии 1

Сервер вызывает `python run_inference.py --request <путь к request.json> --out <путь к каталогу>` с абсолютными путями. Каталог вывода уже создан и пуст. Пример `request.json` и задание для сборки пакета находятся в [промпте для команды](Промпт_для_сборки_модели.md).

- На входе UTF-8 JSON с полями `schema_version` (число `1`), `job_id`, `criteria` (текст) и `files` (список объектов `name` и `path` уже распакованных PDF). Для задания с PDF критериев адаптер `pdf_criteria_runner.py` читает `criteria_pdf` с именем, путём и выбранными страницами и использует разбор критериев из пакета VINITYRAS.
- При успехе код выхода `0` и хотя бы один CSV в корне `--out`. CSV в UTF-8, запятые, уникальные непустые заголовки, одинаковое число полей в каждой строке. Солнечная выгрузка по заданию кейса использует семь CSV из `submission_template`. Для других тем имена и поля определяет критерий. Допустимы таблицы с одними заголовками, когда данных нет.
- При частичном результате можно вернуть `issues.csv` и добавить `report.json` в UTF-8. В отчёте поле `warnings` может содержать массив строк. Бэкенд добавляет в ZIP CSV с данными, `report.json` с замечаниями и `records.json` с привязками. Полный комплект CSV доступен в каталоге результата для проверки по шаблону.
- При сбое верните ненулевой код и напишите причину в `stderr`. Консольный вывод модели сохраняется в `runner.log` внутри каталога задания. Сопоставление с PDF и научные проверки выполняет пакет модели. Сервер проверяет формат выгрузки перед публикацией результата.
